- **单击**进度条轨道中段：播放位置是否跟着跳 → 这条在 2026-10-07 用户实测里被确认为缺陷（点靠近开头的半边跳到开头、点靠近结尾的半边跳到结尾）。**同日晚上已量出根因并修掉**：根因**不是**当初标注为假设的那条 `RangeBase.LargeChange` 翻页（实测 `LargeChange=10` 确实在，但滑块停在 0 时点它右边的 x=0.10/0.25/0.50 `Value` 一动不动，翻页解释直接被否），而是原生"按按下点算分数后再按 `StepFrequency` 量化"——`StepFrequency` 默认 1 配 `SnapsTo=StepValues`（枚举里没有 `None`）在 0..1 的量程上只剩 {0,1} 两个落点，分界正好是几何中点，正对上用户那句「以中间为界」。修法见 §2「进度显示」行。**仪器复量**：点行程 25/50/75% → `Value` 0.2483 / 0.4989 / 0.7494（修前 0 / 0 / 1），每次点击只有一次提交。**这条的最后一半也在 2026-10-07 第二轮复验里报掉了**：播放中点轨道会落到点击处、播放也跟着跳过去（§2.2）。

**唯一的缺陷：单击进度条不落到点上的位置，而是饱和到端点。——2026-10-07 当晚：机制已量出（那条假设被否）、缺陷已修、并用仪器复量过；"听觉跟不跟"那一半由同日的第二轮复验报掉。**
- 现象（用户口径，原话照抄在上面那句里）：以中间为界，点靠近开头的半边 → 跳到开头；点靠近结尾的半边 → 跳到结尾。**位置没有走到点击处**。
- **机制 = 实测，不再是假设**（临时探针读活的 `PositionSlider` + 真机注入鼠标 + 记 `Value` 的每一次变化；原始数字在 `.superpowers/sdd/2026-10-06-d-player-phase20-winui-shell-implementation/click-to-position-report.md`）：
  `Minimum=0 Maximum=1 StepFrequency=1 SnapsTo=StepValues`（`SliderSnapsTo` 只有 `StepValues`/`Ticks` 两个成员，**没有 `None`**）→ 原生把按下点换算成分数之后**按 `StepFrequency` 量化**，在 0..1 的量程上量化结果只有 {0,1}，分界就是几何中点（实测 0.5 归 0）。轨道 `HorizontalTemplate` 904 px、滑块 `HorizontalThumb` 18 px，滑块中心可行程 9..895（与 `Value=0.1637` 时实测中心 154.1 吻合）。
- **那条 `RangeBase.LargeChange` 假设被量否了**：`LargeChange` 实测确实是 10（`SmallChange=1`），但翻页式步进解释不了读数——滑块停在 `Value=0` 时，x=0.10/0.25/0.50 这三点都在滑块**右边**，一次 `+LargeChange` 该把值顶到 1，实测这三点 `Value` **一点没变**；只有 x=0.75/0.90 变成 1。把 `StepFrequency` 单独改成 0.05 / 0.001，同一批点击立刻落到 0.25/0.5/0.75 与 0.248/0.499/0.749 —— 量化才是原因。本文档到这里为止那句"最可能的一条……不是结论，改之前先量"照做了，量出来的结果与它不同。
- **修法（只在壳侧，`D-player.Core` 一个字节没动）**：在比 `Slider` 更深的模板轨道上挂 `PointerPressed`，`e.Handled=true` 把原生那步吃掉（实测吃掉之后 `Value` 的端点事件完全消失），落点由壳自己按测出来的几何算（`clamp((x - thumbWidth/2)/(trackWidth - thumbWidth))`，`x` 相对**轨道元素自己**的边界），照拖动那条路的纪律按住 `IsSeeking`、只经现成的 `SeekCompletedCommand` 提交一次；点 Thumb 上仍旧让给拖动的 `DragStarted/DragCompleted`。另外 XAML 里显式给 `StepFrequency="0.001"`（≈0.9 px 一格）——这一半不是为了单击（单击已经不靠控件算），是为了**拖动**与"轨道找不到时退回原生"那条路不再被量化到端点。拦不住的那两条路也记了实测：挂在 `Slider` 上的处理器动手太晚（`Value` 已被改成端点），托管子类覆盖 `OnPointerPressed` 在这个原生控件上根本不被调用、而且 `DefaultStyleKey=typeof(Slider)` 会让模板变形。
- **修好后的仪器读数**（曲目已载入但没出声：`Duration=00:04:32`）：点行程 25/50/75% → `Value` **0.24830699774 / 0.49887133183 / 0.74943566591**（修前同三点是 0 / 0 / 1），`Position` 00:01:07.5395 / 00:02:15.693 / 00:03:23.8465，每次点击恰好一对 `IsSeeking` True→False（= 一次提交）；按在滑块上 `Value` 不动、0 次 `ValueChanged`；拖到行程 30% → `Value=0.3`。**与名义值差的那约 0.0017 不是映射误差**：注入的指针实际落在请求位置左边约 1.5 px（有效像素→屏幕像素取整），而 0.24830699774 正是 `(229-9)/886` 这个式子在 229 px 上的值。
- **听觉那一半已闭合（第二轮复验）**：上面那些是控件内部读数 + Core 的 `Position` 真的被改成了目标值；**播放中点轨道会落到点击处、播放也跟着跳过去**是用户 2026-10-07 第二轮报的那句。Seek 链上这块从此不再是"只有你能验"，剩下的只是 §4"操作手感"那一维的主观打分。
- 这次顺带量出来的**残留缺陷**（没顺手改）：进度条有键盘焦点时按 → / PageUp 仍旧一步到头（`SmallChange=1`、`LargeChange=10` 这两个默认值本次没动，走的是 `Position_Changed` 那条提交路）。单击与拖动不受它影响。
- 不受影响的相邻两件事：**拖动语义**（A2 那半，且"松手后停在手指处"这次有仪器读数了）与**位置刷新**（播放中进度推进已由 ③ 实测通过）。

**两轮之后：走查里没有待复验项了。仍然站着的只有下面三处，而前两处不是"再验一次"能关的**
- **WinUI 不进任何门禁** → XAML 编译、左栏逻辑、关闭落盘**没有自动回归**；进度条那两条输入路径挂在**两个模板部件名**上（`HorizontalThumb` / `HorizontalTemplate`），部件改名时是**静默退化**（§5 关切 2、5）。上面记的仪器读数只证明"今天这台机器上挂上了"，用户的耳朵与手都替代不了它——这一处只能由门禁或壳侧回归关掉。
- **Windows 应用程序日志 / WER 在本机读不到**（读取被安全策略拒绝）→ "没有崩溃记录"这一条始终**没有取证**；运行期异常在 WinUI 侧也没有可见出口（§5 关切 3）。第二轮那四条是行为层面的观察，不是崩溃记录。

**拿这份材料自己的规则量它自己**：本表的规矩是"把量到的和推出来的分开写"。"单击跳转与 WPF 结果同类"这句话过去靠的是 `IsMoveToPointEnabled`——一个 **WPF** 的属性，WinUI 3 的 `Slider` 上没有（引用即 CS1061）；假依据在 `6484025` 被撤走之后，那一格剩下的正确状态只有"待用户确认"，而**把它落成"不工作"的是用户的实测，不是又一层推理**。上面每一条"通过"都对应一句人话报告，每一条机制解释都带着"假设"的标签——包括这条缺陷的。**这条纪律这次走完了它自己的第二轮**：那条被标注为假设的 `LargeChange` 解释，在动手改之前被实测**否掉**了（`LargeChange` 确实是 10，但滑块停在 0 时点它右边的三个位置 `Value` 一动不动，翻页解释站不住），真正的机制是 `StepFrequency=1` + `SnapsTo=StepValues`（枚举里没有 `None`）的量化；修完之后这一格的状态由"⚠️ 缺陷 + 假设"换成"🟡 已修 + 仪器读数 + 听觉待复验"，**当时没有升成 ✅**——那条 ✅ 要的是用户自己在播放中点一下；同日第二轮用户点了、报了"落到点击处、播放跟着跳过去"，它才走到 ✅。这份表因此现在同时留着四层痕迹：一句被撤走的假依据、一句被实测否掉的假设、一组可复算的仪器读数、和一句用户的复验报告。

**若结论是"停止"**：Phase 20 的 Task 1–2（`D-player.Core` 抽取 + 数据目录参数化）**建议保留**——它们对 WPF 版零行为影响，且让未来任何新壳都更省事；`D-player.WinUI` 工程的去留由你另行决定。

**已知关切（决策时值得计入）**

1. 切片无法自助走通：没有导入入口 + 首启零曲目，不手工放 `queue.json` 就只能验收 §2.1 之外的几项。
2. **WinUI 不进门禁**（设计决策，为了让两条门禁不被 Windows App SDK 工具链拖慢），所以新壳的正确性目前主要靠真机手测 + **一条需要人记得跑的壳侧构建检查**。本波为此把触发条件写死（Core 公开面一变就跑）并给了 `tools/verify-gates.ps1 -Full` 一条命令——但"有规则"和"会执行"之间仍然隔着一只手。
3. 运行期异常在 WinUI 侧没有可见出口（WinExe 无控制台，`Debug.WriteLine` 不进任何流），第二阶段建议先给壳加一条最小崩溃/日志出口。
4. `IFileDialogService` 的同步契约 vs WinUI 异步 picker 是第二阶段的第一个真决策点（改跨壳接口需要单独拍板）。
5. 进度条的两条用户输入路径都挂在 `Slider` 的**模板部件名**上：拖动挂 `HorizontalThumb`（`DragStarted/DragCompleted`），单击挂 `HorizontalTemplate`（`PointerPressed`，见 §2「进度显示」）。部件改名时**静默退化**，而 WinUI 不在门禁里 → 没有自动回归能发现。2026-10-07 的仪器读数确认这两个部件在本机都被找到了（`_positionTrack=HorizontalTemplate / _railHooked=True`，且注入的拖动/点击落点都对），但那只证明"今天这台机器上挂上了"。两条退化方向不同，也都不是灾难：Thumb 找不到 → 拖动退回"连续 Seek"的旧行为；轨道找不到 → 单击退回原生 move-to-point，因 XAML 里显式给的 `StepFrequency=0.001`（≈0.9 px 一格）落点仍在点上，只是精度退到约一个像素——**不会再退回"饱和到端点"**。另外记一条本波量到的事实：`Slider.FindName` 在本壳取不到原生模板部件名（实测返回 null），部件名一靠"向下找第一个 `Thumb`"、二靠"已挂接滑块的可视化父节点"兜底 —— 以后加第三个模板挂接时别假设 `FindName` 能用。
6. **Mica 的本波复探没能复现 Task 4 的位置变化签名**：三个窗口位置下四个采样点全部位置不变（`#202020/#202020/#272727/#272727`）。这**不足以判定材质消失**——采样点很可能都落在不透明层上（内容区 `#272727` 就是 `NavigationView` 的内容卡片层），而 Task 4 当年是挑着"能看见窗外内容"的点采的；但它意味着本表里的 Mica 一行**沿用旧取证、本波未复现**。续投的话，第一件事就该按 Task 4 的三行对照协议（材质+不透明底 / 材质+Transparent / 无材质+Transparent）重做一次，而不是继续引用旧表。
7. 本阶段遗留的其它小项已记在实现台账，见下面那份指名道姓的清单。
8. **2026-10-07 用户实测新增的那条已知缺陷（WinUI 进度条单击定位不工作）当晚已量出根因并修掉**：根因**不是**当时标注为假设的 `RangeBase.LargeChange` 翻页（实测否掉了：`LargeChange=10` 在，但滑块停在 0 时点它右边的位置 `Value` 一动不动），而是原生"按按下点算分数后按 `StepFrequency` 量化"，`StepFrequency=1` + `SnapsTo=StepValues`（枚举无 `None`）在 0..1 量程上只剩 {0,1} 两个落点。修法是壳侧在模板轨道元素上接管这次按下、自己按实测几何算落点、照拖动同一条 `IsSeeking` 纪律经现成的 `SeekCompletedCommand` 提交一次（`D-player.Core` 未改）。仪器复量：点行程 25/50/75% → `Value` 0.2483 / 0.4989 / 0.7494（修前 0 / 0 / 1）。**去留判断时这一格算"已修且已复验"，不算"仍存在"**——听觉那一半由 2026-10-07 第二轮复验报掉（§2「进度显示」、§2.2）。同一天晚上另外量出一条**没顺手改**的残留：进度条有键盘焦点时按 → / PageUp 仍旧一步到头（`SmallChange=1`/`LargeChange=10` 未动，列在下面收尾清单）。

**收尾任务清单（本波判定为"记录、不修"，逐项指名）**

*需要单独拍板的（跨壳 API / 两壳对称性）*
- **WPF `App.OnExit` 的同步 Dispose 缺陷**（`App.xaml.cs:61-67`：容器里住着只实现 `IAsyncDisposable` 的 `MainViewModel` → 抛异常 → 退出码非 0）。**这是 §2"退出与收尾"一行里 WPF 那侧的 ⚠️**，Phase 20 之前就存在、刻意没复制进第二壳、也刻意没在本波修：数据已落盘，属"难看但真"的缺陷，修它要连着看两壳的关闭路径。
- **`DPlayerDataPaths` 的空 `FolderName` 逃生门与构造形态**（整支分支评审的 Important 6，以及它吸收掉的若干台账 minor）。这是 Core 的 API 重设计，会同时波及两个壳，放在一个以"WPF 零变化"为前提的阶段末尾做，风险不对称 → 独立任务。
- **第二次关闭请求可能截断 flush**（`MainWindow.xaml.cs` 的 `if (_isClosing) return;` 未 cancel 第二次请求）——**与 WPF 的 `Views/MainWindow.xaml.cs:85` 同形**，所以只修一个壳会制造新的不对称；要修就两壳一起（`_cleanupDone` 标志）。

*第二阶段结构性工作（不影响本次去留判断）*
- **进度条的键盘步进仍旧饱和到端点**（2026-10-07 随单击定位一起量到的，**记录、没改**）：`SmallChange=1` / `LargeChange=10` 是 WASDK 2.5.1 在本壳上实测读到的默认值，方向键 / PageUp 走的是 `Position_Changed` 那条提交路，所以一次按键就把位置顶到头。修法与单击同源且更小（把这两个默认值显式给成千分之一程，或让键盘也走壳侧算好的落点），但它既不是用户报的那条、也没有 WPF 侧的对照读数（WPF 的键盘步进用的是 `SmallChange`，同样没人量过），所以留成单独一条，等两壳一起看的时候再定。
- 左栏每次点击整栏重建（pane rebuild-per-click）；`MainWindow.xaml.cs` 单文件承载过多职责 → 抽 `PlayerBar`；左栏改声明式（数据驱动）；`NavigationViewItem.Content` 的重命名快照陈旧问题；VM 订阅无解绑路径；`Debug.WriteLine` 作为"恢复被跳过"的唯一信号（WinExe 里等于没有）；`Directory.Build.props` 统一包版本与 glob 排除集（现在是三处副本）。
