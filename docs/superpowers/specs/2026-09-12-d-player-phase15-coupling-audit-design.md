# Phase 15：耦合健康度审计（Coupling Health Audit）设计

> 设计日期：2026/09/12 · 对应分支：`master` · 状态：**待实现**
>
> 目标：对当前代码库做一次**客观、可复现**的耦合健康度审计——度量依赖结构、检测相对 `docs/COUPLING.md` 的漂移、裁决 5 个既定决策点，并给出明确的「解耦 / 不解耦」结论。

---

## 0. 背景与基线

`docs/COUPLING.md` 是项目的**活耦合登记册**（每次 phase 更新，现对应 Phase 14）：TL;DR 评级「耦合度=低、无需立即重构」、依赖图、5 项技术债（全清）、2 项过度抽象（`IAudioDeviceManager` / `IAudioOutputFactory` stub，注册但无人消费）、约 60 条隐式契约、启动检查清单。

**Phase 15 不与 COUPLING.md 重复劳动**：它不是重读结论，而是**用客观证据重新验证结论是否仍成立**——

1. 用脚本度量依赖结构（环、层级违规、接口宽度、文件规模、DI 注册-消费差），产出可复现的原始指标；
2. 对 COUPLING.md 做**漂移检测**（§5 隐式契约与代码是否仍一致；Phase 14 是否引入未登记契约）；
3. 对 5 个既定决策点做**裁决**（含明确的判定标准），输出「解耦 / 不解耦」结论。

**决策框架（方案 C，混合）**：
- **客观结构性违规零容忍**：依赖环、层级违规 = 「必须修」（另立重构任务，不在 Phase 15 内改功能代码）。
- **宽度 / 规模用软阈值 + 人工裁决**：给出建议与理由，不强制为凑阈值而重构。

---

## 1. 目标与范围

### Goals
- 产出 7 项客观度量指标（依赖图 / 环 / 层级违规 / 接口宽度 / 文件规模 / DI 注册-消费差 / 隐式契约漂移）。
- 裁决 5 个决策点（D1–D5），每点给出 verdict + 理由。
- 交付 Phase 15 审计报告（原始指标 + 方法学）+ 更新 COUPLING.md（verdict / 决策 / 新契约 + 链接）。
- 提交一个**可复跑**的审计脚本，供后续 phase 复用。
- 给出总体结论：耦合是否仍健康、是否需要解耦。

### Non-Goals
- 不在 Phase 15 内修改功能代码（审计只读 + 产出文档/脚本）。
- 不引入重型静态分析工具链（如 NDepend / Roslyn 全量分析器）——用轻量脚本即可。
- 不重做 COUPLING.md 已有且仍成立的内容（仅刷新 verdict / 补漂移 / 记决策）。
- 若发现「必须修」的违规，**只立项**（另立重构任务），不在本 phase 实施。

## 2. 度量指标与脚本

提交一个轻量、可复跑的 **PowerShell** 分析脚本（置于 `tools/coupling-audit/`），解析源码产出以下指标。脚本只读源码、不改代码。

| # | 指标 | 方法 | 期望 / 基线 |
|---|------|------|------------|
| M1 | **依赖图** | 解析各层（Models/Services/ViewModels/Views/Configuration/Extensions/Converters）的 `using DPlayer.*` 与跨层类型引用，建有向图；计算每类型 fan-in / fan-out | 与 COUPLING.md §2 依赖图一致；无意外新边 |
| M2 | **环检测** | 在类型/命名空间依赖图上找环 | **0 环**（零容忍） |
| M3 | **层级违规扫描** | 断言：Services 不引用 ViewModels/Views；ViewModels 不引用 Views；Views 仅经 DataContext / `App.GetService` 触 VM；Models 为基座被各层引用（允许） | **0 违规**（零容忍） |
| M4 | **接口宽度** | 统计 `IPlaybackService` 等核心接口成员数，与历史对比 | `IPlaybackService` 现 **20** 成员；看增长趋势 |
| M5 | **文件规模/职责** | 每文件 LOC；标记 >600 行做职责复核 | PlaylistVM ~564、PlaylistsVM ~468、NAudioPlayback ~307、PlayerVM ~350、EqualizerDialog.cs ~260（脚本算精确值） |
| M6 | **DI 注册-消费差** | 对比 `ServiceCollectionExtensions` 注册的服务 vs 全仓消费点，检出「注册但无人消费」 | 应复现 §4 的 2 个 stub（`IAudioDeviceManager`/`IAudioOutputFactory`） |
| M7 | **隐式契约漂移** | 人工核对 COUPLING.md §5 各条与代码是否仍一致；补登 Phase 14 后新增未登记契约 | 全部一致或补登；无静默失效契约 |

> M1–M6 由脚本客观产出；M7 为人工核对（脚本可辅助定位，判定靠人）。

## 3. 五个决策点与判定标准

| # | 决策点 | 判定标准（框架 C） | 当前基线 |
|---|--------|-------------------|---------|
| **D1** | `IPlaybackService` 接口宽度 | 成员数 >24 **或** 第 3 个 DSP/可视化关注点接入 → 建议拆分（如分离 effects/分析关注点）；否则记为可接受单一播放门面 | 20 成员 |
| **D2** | 2 个 stub 去留（`IAudioDeviceManager`/`IAudioOutputFactory`） | 若多设备/输出模式仍在近期路线（PROJECT.md §1.2 后续增量）→ 保留；否则建议删（YAGNI）。产品决策：审计给建议、用户裁决 | 保留（COUPLING §4 现状） |
| **D3** | 隐式契约漂移 | §5 任何条目与代码不符、或有新增未登记契约 → 补登/修正 | 待审计核对 |
| **D4** | 依赖环 / 层级违规 | **零容忍**：发现即「必须修」，另立重构任务 | 期望 0 |
| **D5** | 职责过载文件 | >600 行 **且** 多职责 → 建议拆分；否则记为观察项 | PlaylistVM ~564（接近阈值，重点复核） |

## 5. 流程与验证

1. 编写审计脚本 → 跑 M1–M6，记录原始指标。
2. 人工核对 M7（隐式契约漂移）+ 复核 M5 标记的大文件职责。
3. 按 §3 标准裁决 D1–D5，写 verdict + 理由。
4. 写审计报告；更新 COUPLING.md（摘要）。
5. 若有 must-fix（D4）或裁决拆分（D1/D5）→ 另立重构任务清单（不实施）。
6. **验证**：审计不改功能代码 → `dotnet build` 0 错误 + `dotnet test` 96 全绿应保持；审计脚本可复跑（重跑结果一致）。

## 6. 预期结论（供参考，以审计实测为准）

- 耦合**大概率仍为低**、**无需大解耦**（架构纪律良好，Phase 13/14 均「加功能不触碰核心架构」）。
- **D1（IPlaybackService 宽度=20）** 最可能列为「观察项/候选」：尚未到拆分阈值，但 DSP/可视化配置持续往单接口挂，值得记录趋势。
- **D2（stub）** 倾向保留（多设备仍在 PROJECT.md §1.2 路线），除非用户 deprioritize。
- **D4** 期望 0 违规；**D3** 期望无漂移或仅少量补登。

---

## 7. 风险与边界

- 审计脚本解析 `using`/类型引用为**启发式**（非完整语义分析），可能对同层/嵌套引用有噪声；以人工复核 M5/M7 兜底。
- 审计**只读**；任何代码改动都走独立重构任务（TDD + 双阶段审查），不混入本 phase。
- 不追求指标完美；目标是「有证据的结论 + 明确决策」，而非数字游戏。
