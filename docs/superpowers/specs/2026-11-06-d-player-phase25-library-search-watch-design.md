## 1. 已确认的范围

本阶段交付两项相互衔接的功能：在内存音乐库中全局搜索，以及文件系统路径变化后自动更新音乐库。

| 决策 | 本期约定 |
|---|---|
| 开发范围 | 共享 Core + WPF 主壳；不新增 WinUI UI |
| 搜索形态 | 独立的全局搜索页，按艺术家、专辑、曲目分组 |
| 监听粒度 | 每个规范化库根递归监听；按根去抖后重扫受影响根，不是逐路径修改索引，也不是每次整库刷新 |
| 缺失文件 | 不主动中断当前播放；库视图移除失效项，库播放队列不随监听重排或删除 |
| 队列入口 | 延后；隐藏库播放队列继续沿用现有控制与持久化 |

不做：各页面单独筛选框、拼音/罗马字/模糊搜索、搜索历史、第三方全文索引、标签编辑及同路径标签内容变更监听、库队列管理 UI、拖拽入队、封面缓存项目、专辑网格虚拟化项目、输出模式/网络流播放。

不更改专辑分组规则、音频输出链、EQ/频谱、可见歌单的组织形式；不新增 NuGet 包。文件夹绑定歌单不新增实时监听，只做共享缓存所需的窄范围一致性修正。

## 2. 当前实现与承重点

| 当前事实 | 设计约束 |
|---|---|
| [LibraryViewModel](../../../D-player.Core/ViewModels/LibraryViewModel.cs) 持有按路径去重的曲目、缓存条目、艺术家/专辑集合与四种页面；扫描后调用 `RebuildGroups()` | 搜索使用这些内存数据，不为每次键入读盘；自动刷新不得清空查询词 |
| [LibraryScannerService](../../../D-player.Core/Services/LibraryScannerService.cs) 提供 `ScanFolderWithStatus`、`ComputeDiff`、`ReadMetadataBatchAsync` | 复用根级扫描和差分；不可用根与空根必须区分 |
| `ComputeDiff` 比较路径，并重读零时长且无采样率的条目；没有文件长度/修改时间指纹 | 本期不承诺检测同路径的有效标签改写；不能宣称一次手动刷新一定会重读这类文件 |
| [LibraryPathNormalizer](../../../D-player.Core/Services/LibraryPathNormalizer.cs) 只去重相同根，保留父子嵌套根 | 根不能视为互斥；合并库时按完整路径去重，删除一个根的数据不能误删其他根仍持有的条目 |
| [LibraryGrouping](../../../D-player.Core/ViewModels/LibraryGrouping.cs) 以规范化专辑标题 + 曲目直接父目录分组 | 专辑选择、搜索跳转、刷新后的详情恢复不能仅以标题或标题 + 艺术家定位 |
| [JsonLibraryCache](../../../D-player.Core/Services/JsonLibraryCache.cs) 是共享单例，按根存条目；`LoadAsync`/`SaveAsync` 分别加锁，不等于扫描事务锁 | 音乐库与文件夹歌单扫描不能互相覆盖过期结果；缓存不是任何一个可见集合的成员列表 |
| [PlaylistsViewModel](../../../D-player.Core/ViewModels/PlaylistsViewModel.cs) 的文件夹歌单只有启动/手动重扫；其差分目前直接驱动队列增删 | 新库 watcher 不得调用这个会改队列的入口；必须验证共享根缓存先被库更新时，歌单后续手动刷新仍能正确增删 |
| [MainViewModel](../../../D-player.Core/ViewModels/MainViewModel.cs) 关闭时保存 `Library.Page.ToString()`，恢复只认原四种页 | 搜索必须是临时状态，不能直接把 `Search` 保存成一个无法恢复的页面 |
| [PlaylistViewModel](../../../D-player.Core/ViewModels/PlaylistViewModel.cs) 的 `PlayTrackAtAsync` 已有装载失败跳过、连续失败最多三次的边界 | 复用既有失败行为；不增加无限跳过，也不承诺删除后仍能从已失效路径重新装载 |

## 3. 搜索行为

### 3.1 查询与结果

- 库视图头部常驻一个搜索框，提示文案为「搜索艺术家、专辑或曲目」，有可点击的清空按钮；原有刷新按钮保留。
- 查询去除首尾空白；空字符串或全空白表示退出搜索，不返回整个库作为搜索结果。
- 使用 `OrdinalIgnoreCase` 子串匹配；内部空格是普通字符，不分词、不支持正则或通配语法。中文、日文按原文字面匹配，不做读音转换。
- 输入停止 200ms 后重算；IME 组合输入完成后再提交有效查询。搜索仅匹配内存文本，不扫描目录、不读取标签或封面。
- 三类结果分别去重，同一词可以同时命中三组：

| 分组 | 匹配字段 | 身份与显示 |
|---|---|---|
| 艺术家 | 显示名称 | 沿用既有艺术家身份；名称 + 专辑/曲目计数 |
| 专辑 | 显示标题、显示艺术家 | 标题 + 直接父目录身份；显示封面、标题、艺术家/年份 |
| 曲目 | 标题、艺术家、专辑 | 完整路径身份；显示标题、艺术家、专辑、时长和当前播放标记 |

- 未知艺术家/未知专辑可以通过其现有占位名称匹配。专辑行匹配显示艺术家；合辑的各贡献者仍可从艺术家组和曲目组找到，不新增 AlbumArtist 语义。
- 艺术家和专辑结果沿用现有分组顺序；曲目按标题、艺术家、专辑的当前文化大小写不敏感顺序排列，以完整路径的 `OrdinalIgnoreCase` 比较作最终稳定次序。
- 不按相关性打分，不静默截断结果。显示三组命中数、无结果提示；各组布局必须可滚动到末尾，低窗高不能遮挡操作。
- 复用现有深色行/专辑样式与封面惰性加载，不因搜索主动预读全库封面。新增结果区不能通过一次性生成全部隐藏项来换取简单布局。

### 3.2 页面状态与导航

新增 `LibraryPage.Search` 和可观察查询/三组结果状态。进入搜索前保存一份非搜索浏览位置：页面、艺术家身份、专辑身份、专辑是否从艺术家页进入；这是会话内的返回快照，不保存对象引用作为长期身份。

| 操作 | 结果 |
|---|---|
| 在任一库页面输入首个有效查询 | 保存该浏览位置并进入 Search；继续编辑只更新结果，不重复覆盖返回快照 |
| 搜索框清空、按 Esc 或搜索页返回按钮 | 清除查询并回到进入搜索前的位置；目标已消失时按原页面回落艺术家/专辑列表 |
| 激活艺术家或专辑结果 | 单击结果或选择后按 Enter 打开对应详情，并清空搜索；这一动作不先恢复搜索前页面 |
| 从搜索打开详情后按返回 | 艺术家详情回艺术家列表；直接打开的专辑详情回专辑列表；艺术家详情再钻入专辑则保留原有返回链，不恢复旧查询 |
| 双击曲目结果或在选中曲目上按 Enter | 保持搜索页和查询，按该曲目的完整专辑上下文开始播放 |
| 点击侧栏艺术家/专辑节点 | 清除查询，显式进入指定列表，不恢复旧搜索快照 |
| 点击可见歌单切出库视图 | 清除查询并结束本次搜索；不改正在播放的上下文 |

`Ctrl+F` 仅在库视图活动且没有模态对话框时聚焦搜索框；Esc 只处理搜索清空，不吞掉 IME 取消和其他对话框的按键。单击曲目只选中，不起播；空白处双击不沿用旧选中项播放。搜索框里的 Space 是输入字符，不能触发播放器快捷键。

### 3.3 播放与重启恢复

- 激活曲目结果时，按路径在最新库快照中重新解析其所属专辑及索引，调用既有 `PlayLibraryTracksAsync`；入队的是完整专辑，不是所有搜索结果，也不是只命中的曲目。
- 用户激活前结果已被监听移除时，不播放旧索引对应的另一首；更新结果并给出「该曲目已不在音乐库中」的非模态提示。
- 播放后编辑/清空查询、库后台更新均不重建已经开始播放的库队列。当前播放标记继续按库播放归属 + 文件路径计算。
- 查询词、搜索结果和搜索模式不写入 settings/queue/cache。关闭时若停在 Search，`MainViewModel` 保存进入搜索前的有效非搜索导航快照；若已进入搜索结果详情，保存当前详情。
- 保持现有 `AppSettings.LibraryView*` 字段及原四种页的恢复语义；找不到详情时回落对应列表，不为 Search 新建持久化 schema。

## 4. 实时监听与调度

### 4.1 职责划分

- Core 新增 `ILibraryWatcher` 及基于 `FileSystemWatcher` 的实现：负责启动/替换根集合、递归订阅、发出根失效/错误通知、释放句柄。构造和 DI 解析本身不启动监听。
- 去抖、pending 根集合与扫描顺序由可独立测试的库刷新调度逻辑负责；原生事件处理器不得枚举文件、读标签、写缓存或修改 UI 集合。
- `LibraryViewModel` 负责应用根快照、分组、查询结果与状态行；`LibraryScannerService` 继续负责实际目录枚举、差分和标签读取。
- `ILibraryCache` 的持久化格式保持不变。共享根扫描的排他性见 §5，不另建第二套缓存文件或搜索数据库。

### 4.2 事件范围

- 每个规范化且可用的库根一个 watcher，递归监听文件名和目录名变化：Created、Deleted、Renamed，以及 watcher Error。
- 音频扩展名沿用 `AudioConstants.AudioExtensions`。改名时旧路径或新路径为支持格式都要触发；目录移动/改名要覆盖整棵子树，不能仅检查目录名扩展名。
- 已删除路径无法再检查类型时，允许保守地标记所属根待扫，不能因无法判断它曾是目录而漏掉变化。
- 普通内容写入/标签 Changed 不在本期范围；不使用修改时间指纹扩展缓存 schema。复制尚未完成的处理见 §6。
- 含嵌套根时，将事件关联到受影响的所有已配置根：按路径分隔符边界判断包含关系，不能用裸字符串前缀把相邻同前缀目录误判为子目录。

### 4.3 去抖与扫描顺序

1. 每个根独立计算 800ms 静默窗口，重复事件合并为一个待扫描根；一个根持续变化不能重置其他根的等待时间。
2. 每根从首个待处理事件起最多等待 5s，即使事件持续也启动一轮校准；扫描中再来的事件保留为下一轮 pending，不丢弃。
3. 库扫描使用一个异步串行执行通道，覆盖启动扫描、手动刷新、设置根变化与监听触发。磁盘枚举、标签和分组计算不在 WPF UI 线程执行；发布可观察状态时回 UI 上下文。
4. 手动全量刷新/根集合变更优先于尚未开始的监听扫描。被替代任务在可取消边界结束；不能取消的标签调用结束后检查代际，旧代结果不得发布。
5. 整库刷新期间仍接收事件并标 pending；刷新结束后补扫仍需校准的根。事件不能因为一次刷新开始就被直接清空。
6. 同一批根扫描结束后合并发布库状态，再按当前查询重算一次搜索。没有路径或元数据差异时不反复清空集合、失效封面或刷新结果。

“实时”表示自动最终一致，不是逐事件立即反映。800ms 是开始处理的去抖时间；总延迟还包括枚举、标签读取和 UI 发布，不能把约 1s 写成任意大库或网络根的硬保证。

### 4.4 启动、根变更与退出

- 监听只由 WPF 启动链显式启用，不因共享 `MainViewModel` 被 WinUI 解析而自动启用。WinUI 保留原有库启动扫描行为，不新增 watcher 后台工作。
- 启用时先订阅 watcher，再安排根校准，避免启动扫描与订阅之间漏事件：尚未开始的启动扫描可合并；若该根已开始扫描，则在其后补一次校准。
- 库页不可见、切换到歌单时 watcher 仍工作，不绑定 `LibraryView.Loaded/Unloaded`。没有库根时不创建 watcher。
- 设置保存后仍由 `RefreshIfRootsChangedAsync` 判断根集合是否变化；仅改音量/频谱不重建 watcher、不触发扫描。真实根变化才替换订阅并校准；旧根回调通过根集合代际丢弃。
- 退出先禁止新事件入队，取消去抖和待处理任务，解绑并释放 watcher；然后等待已经开始的库扫描/原子缓存写收尾，不再发布 UI 状态。
- 需要等待的工作由 `MainViewModel.CleanupAsync` 异步接入，不能在 UI 线程使用同步 Wait；清理应可重复调用，晚到回调无效。

## 5. 根快照、共享缓存与分组一致性

### 5.1 根级增量的真实含义

- 对受影响根完整枚举支持格式路径，再与该根上一份有效快照/缓存元数据做差分；未变且元数据有效的文件不重读标签。
- 普通监听更新不调用会重载所有根缓存的 `RefreshAsync()`，也不调用文件夹歌单的重扫方法。
- 维护每根快照后按规范化文件路径合并全库：同一路径只计一次；一个根退出仅移除它的成员资格。不可用根保留最后有效快照。
- 一批受影响根全部完成后再合并，避免移动文件在多根结果之间重复计数。嵌套根同一路径的元数据沿用确定性的配置根顺序选取；这些根必须共同参与相关路径的校准。
- 本期允许全量内存重分组；“根级增量”不等于局部更新每个艺术家对象。无差异不重建，封面按仍有效的专辑身份保留，受影响或首曲变化的专辑重新走惰性读取。

### 5.2 与文件夹绑定歌单共用缓存

缓存只表示某根一次扫描取得的元数据，不表示任何播放队列当前已经拥有这些成员。

- 音乐库与文件夹歌单对同一规范化根的扫描、差分和缓存保存必须共用根级排他区域；仅靠 `JsonLibraryCache` 两个方法各自加锁不足以防止旧扫描后写覆盖新扫描。
- 排他区域一次只持有一个根，既有缓存文件锁仍负责不同根条目的读改写；不引入跨根嵌套锁。
- 文件夹歌单启动/手动刷新对队列的增删应比较“本队列路径集合”和“本次成功枚举路径集合”，缓存仅用于复用元数据。否则库先更新缓存后，歌单看见空差分会漏增漏删。
- 这一修正只保证原有刷新入口的正确性，不让库 watcher 自动同步可见歌单，不改变歌单手动排序、当前项与现有刷新入口的控制权。
- 库发布使用自己的根快照，不能因共享缓存被其他消费者保存而丢失尚未应用到自己的变化。

### 5.3 并发发布与选择保留

- 根集合代际、库快照版本、查询版本分别表达不同失效原因：根被移除、数据变更、用户改词不能互相混用。
- 扫描结果在写缓存与发布 UI 前检查是否仍属当前代；已进入原子保存的操作先收尾，再执行更新一代的校准。完成清理后不得再启动保存。
- 搜索读取不可变快照；晚到的旧查询或旧库版本结果不得盖掉新查询。UI 回调内仍须核对版本，不能只在投递前检查。
- 刷新后的艺术家详情按艺术家身份重定位；专辑详情、搜索来源快照按标题 + 直接父目录重定位。当前 `RebuildGroups()` 的标题 + 艺术家查找不足以区分同名专辑，本期必须同步改正该关联处。
- 目标详情消失则回落所属列表；搜索结果随最新快照更新。既有曲目播放、进度、随机/循环与队列索引不受这些 UI 关联变化影响。

## 6. 错误与外部文件边界

| 情况 | 行为 |
|---|---|
| 可枚举但为空的根 | 视为真实空集合，更新该根快照与缓存 |
| 根不存在、无权限、枚举异常或失联 | 保留该根最后有效快照/缓存，标为不可用；不把失败当成全根删除，不影响其他根 |
| watcher 缓冲区溢出 | 标记该根需要重新校准，合并为根级重扫；不尝试重放丢失事件 |
| watcher 无法创建或已失效 | 显示「部分文件夹未能自动监控，请手动刷新」；手动刷新/根设置变化/下次启动重试订阅，无高频重连循环 |
| 根重新接入 | 若原订阅未失效则按事件校准；已失效订阅需要上述显式重试，不承诺后台自动发现所有重接入 |
| 新文件仍在复制、标签暂不可读 | 不影响其余文件；保留文件名 fallback。为本批无有效元数据的新文件最多在 1s、3s 后各安排一次该根补扫；仍失败保留 fallback，后续事件/手动刷新再试，不无限重扫 |
| 缓存写失败 | 保留本轮有效内存结果、标记缓存未保存；后续扫描再尝试，不把 UI 更新报告为持久化成功 |
| 查询无命中 | 显示无结果而非库为空；查询与监听均保持有效 |
| 网络根通知不可靠 | best-effort；保留手动刷新，不承诺跨网络断连无遗漏 |

删除/改名文件只改变库的视图与缓存，不主动调用播放器 Stop/Pause/Unload，也不修改已建立的库播放队列；应用不能保证操作系统允许删除打开的文件，或底层解码器在外部文件破坏后仍可播放。

下次装载不存在的队列项时复用现有失败跳过逻辑，连续三次失败后停止；原路径改名后不自动重写正在播放的队列路径。本期不新增通用播放错误通知系统，监听/扫描错误由库状态行表达，不能把“已有播放错误事件”写成“已有 WPF 用户提示”。

### 8.1 默认自动测试

### 8.2 WPF 人工验收清单

1. 艺术家/专辑/曲目查询均可达，中文和日文输入正常；清空、Esc、Ctrl+F、Enter、鼠标路径符合 §3。
2. 从四种库页进入搜索后清空，回到正确页；从搜索打开详情后返回不复活旧查询；搜索页关闭重启恢复非搜索导航。
3. 双击搜索曲目后，上下首按完整专辑顺序运行；编辑查询和自动更新不改变播放队列、当前曲或进度。
4. 在隔离小型测试库新增/删除/改名文件、改名含子目录的专辑目录，观察结果和计数最终收敛；记录通知到可见更新的实际延迟。
5. 两根仅一根改变时，扫描证据只包含受影响根；父子嵌套根不重复计数，移除一根不丢其他根持有的成员。
6. 打开专辑详情时变更其他文件，详情不串到同名专辑，封面不无故清空；当前详情真正消失时回落正确。
7. 小高度/窄窗口下搜索框、刷新/清空、分组结果可达；长名称不挤坏布局，无结果状态不会遮住导航。
8. 设置只改音量/频谱不重扫、不重启 watcher；手动刷新仍有效；歌单切换/排序/文件夹刷新、断点续播和启动无闪屏不回退。
9. 根不可用/订阅失败时有明确状态且缓存保留；播放中的文件外部消失时，代理不把“未主动停止”冒充底层音频一定不断。
10. 测试监听退出和重新启动，不残留文件句柄；失败、慢扫描、复制未完成分支保留各自证据边界。

仅使用新建临时库和合成音频构造破坏性场景，不删除/改名用户真实曲目，不改用户目录权限；不直接读写受限的应用数据目录。临时截图/脚本的清理与证据失效需在验收记录中明确。UI、听感、内部状态与测试结果分别报告，不用构建通过替代 UI 验收。
